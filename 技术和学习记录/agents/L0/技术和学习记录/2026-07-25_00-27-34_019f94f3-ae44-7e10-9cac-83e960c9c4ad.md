### Assistant final（完成）

明白了，你问的是：**在还没做 A/B 实验之前，为什么会把 MCP 列为嫌疑对象？**

主要是两个线索同时出现：

1. **故障发生的阶段很特殊**

   - `opencode models` 成功：模型提供商、认证和模型目录没问题。
   - ACP `initialize` 成功：OpenCode 进程、CLI 路径和通信协议没问题。
   - 只有 `session/new` 卡住。

   `session/new` 不只是“读取模型列表”，它还要组装一个完整会话，加载工具、agents、MCP 等会话级组件。因此卡在这里时，我会优先怀疑“只有创建会话才启动的外部组件”，而 MCP 正是最典型的一类。

2. **OpenCode 日志刚好出现了 MCP 启动失败**

   在 Claudian 启动 ACP 的同一段日志中，出现：

   ```text
   server unavailable key=blender-mcp type=local status=failed
   ```

   这不是直接证明，但它与卡点高度吻合：模型命令不需要建立 Blender MCP 会话，所以能成功；Claudian 为发现模型创建 ACP 会话时，会触发会话组件初始化，于是可能被失败的外部 MCP 拖住。

所以最初的思路其实是：

```text
模型和认证正常
→ ACP 基础连接正常
→ 只在创建完整会话时挂起
→ 查看“会话创建新增了什么”
→ 日志同时报告 blender-mcp unavailable
→ 优先验证 MCP 假设
```

换句话说，**“阶段边界”让我想到会话级组件，日志警告让我把 MCP 排到第一位**；后面的单变量实验才把这个直觉升级成结论。

### 对抗性审查

- `blender-mcp` 日志警告本身也可能只是无关噪声，很多程序能容忍某个 MCP 离线，因此当时只能称为假设。
- 其他会话级组件，例如 agents 配置、数据库或权限初始化，也可能造成相同卡点，所以我没有仅凭警告直接修改配置。
- 最终是“禁用所有 MCP 后成功、只禁用 Blender 后仍成功”的对照实验排除了这些替代解释。对“为什么最初想到 MCP”的解释保留，证据链清楚。
